# Архитектура проекта (Feature-Sliced Design)

Проект использует упрощенную методологию Feature-Sliced Design (FSD). Код разделен на слои, которые имеют строгую иерархию импортов.

## Слои (от высшего к низшему)

1. **app/** — Инициализация приложения: провайдеры, роутер, глобальные стили, Redux store.
2. **pages/** — Страницы приложения (композиция виджетов и фич).
3. **widgets/** — Самостоятельные крупные блоки интерфейса (Header, Sidebar).
4. **features/** — Действия пользователя, несущие бизнес-ценность (форма поиска, добавление слова).
5. **entities/** — Бизнес-сущности (Курс, Слово, Пользователь) — их UI и модели данных.
6. **shared/** — Переиспользуемый код, не привязанный к бизнес-логике (UI-кит, хелперы, базовый API-клиент, конфиги).

## Правило зависимостей (Главное правило)

Слой может импортировать код **только из слоев, которые находятся НИЖЕ него**.

- `app` может импортировать всё.
- `pages` могут импортировать `widgets`, `features`, `entities`, `shared`.
- `widgets` могут импортировать `features`, `entities`, `shared`.
- `features` могут импортировать `entities`, `shared`.
- `entities` могут импортировать **только** `shared`.
- `shared` **не импортирует ничего** из других слоев (это фундамент).

## Правило: когда использовать `interface`, а когда `type`

В проекте принято следующее соглашение:

- **`interface`** используется для описания формы объектов (сущностей домена).
  _Пример: `Course`, `Teacher`, `User`, `Group`._
  _Почему:_ Интерфейсы лучше подходят для декларации структур данных, которые могут быть расширены (например, при помощи `extends`), и они дают более читаемые сообщения об ошибках в редакторе.

- **`type`** используется для всего остального:
  1. **Объединения (Union types):** когда переменная может принимать одно из нескольких конкретных значений.
     _Пример: `CourseLevel = 'A1' | 'A2' | 'B1' | 'B2' | 'C1' | 'C2'`._
  2. **Утилитарные типы:** когда мы создаем новый тип на основе существующего (с помощью `Omit`, `Pick`, `Partial`).
     _Пример: `CreateCourseData = Omit<Course, 'id'>`._
  3. **Кортежи и примитивы:** _Пример: `type ID = string | number`._

  ## Правило: выбор индикатора загрузки (скелетон или спиннер)

В проекте используются два типа индикаторов загрузки. Выбор зависит от того, **что именно загружается** и **как долго** это происходит.

### 📌 План для страницы курса (эпик 6)

Когда на странице курса появятся реальные данные (запрос к API), необходимо внедрить следующие индикаторы:

1. **Загрузка данных курса:**
   - Пока `loader` или запрос к API выполняется, вместо контента страницы показывать **скелетон текстового блока** (`TextSkeleton` из `shared/ui/states/text-skeleton`).
   - **Почему скелетон, а не спиннер:** Страница курса — это большой блок текста (описание, программа, преподаватели). Скелетон покажет структуру будущего текста и снизит «прыжок» контента (layout shift), что важно для читабельности.

2. **Кнопка «Записаться на курс»:**
   - Во время отправки формы (POST-запрос) кнопка должна блокироваться и показывать **встроенный спиннер** (`Spinner variant="inline"` из `shared/ui/states/spinner`).
   - Текст кнопки в этот момент меняется на «Отправка...».
   - **Почему спиннер, а не скелетон:** Кнопка — это локальное действие. Скелетон внутри кнопки был бы избыточен и визуально «тяжел». Спиннер компактен и сразу даёт понять, что запрос выполняется.

## Параметры пути vs query-параметры: правило выбора

В проекте принято четкое разделение между параметрами пути (path params) и query-параметрами (search params). Это разделение помогает сохранять URL осмысленным и предсказуемым.

### 📍 Параметры пути (`/courses/:courseId`)

**Назначение:** Идентифицируют **конкретный ресурс** (сущность).

**Когда использовать:**

- Нужно открыть страницу конкретного объекта (курс, слово, пользователь).
- Без этого параметра страница не имеет смысла (нельзя показать «курс вообще»).
- Параметр является частью «адреса» ресурса в иерархии.

**Примеры:**

- `/courses/5` — курс с ID 5.
- `/dictionary/word/hello` — слово «hello» в словаре.
- `/profile` — личный кабинет (без параметра, но это ресурс «мой профиль»).

**Тип:** всегда **строка** (даже если это число). Из-за `noUncheckedIndexedAccess` может быть `undefined`, поэтому нужна проверка (ранний возврат или fallback).

### 🔍 Query-параметры (`?level=B2&page=2`)

**Назначение:** Определяют **способ отображения** ресурса (фильтры, сортировка, пагинация, поиск).

**Когда использовать:**

- Нужно отфильтровать список (по уровню, категории).
- Нужно переключить страницу пагинации.
- Нужно передать поисковый запрос.
- Параметр **не обязателен** для существования страницы (без него показываем «все» или дефолт).

**Примеры:**

- `/courses?level=B2` — каталог курсов, отфильтрованный по уровню B2.
- `/courses?page=2` — вторая страница каталога.
- `/dictionary?search=hello` — поиск по словарю.
- `/courses?level=B2&page=2` — комбинация фильтра и пагинации.

**Тип:** всегда **строка** (или `null`, если параметра нет). Читается через `useSearchParams().get('key')`. Валидация обязательна (если значение не из допустимого набора — игнорировать или сбрасывать).

### 💡 Правило в одной фразе

> **Путь** отвечает на вопрос «**что** показать» (какой ресурс).  
> **Query** отвечает на вопрос «**как** показать» (фильтр, сортировка, страница).

### 🧪 Пример для страницы курса

- `/courses/5` — «показать курс №5» (путь).
- `/courses/5?tab=program` — «показать курс №5, вкладка "Программа"» (query).
- `/courses?level=B2` — «показать список курсов, отфильтрованный по B2» (query, потому что это список, а не конкретный курс).

### ⚠️ Антипаттерны

- ❌ `/courses/level/B2` — уровень не является ресурсом, это фильтр. Используйте `/courses?level=B2`.
- ❌ `/courses?id=5` — ID курса — это ресурс, он должен быть в пути: `/courses/5`.
- ❌ `/courses/5/level/B2` — смешение ресурса и фильтра. Лучше `/courses/5?level=B2` (если фильтр относится к курсу) или `/courses?level=B2` (если к списку).

### 🦴 Скелетон (`CardSkeleton`, `TextSkeleton`)

Используем, когда загружается **целый блок контента** (карточки, текст, таблица) и важна плавность. Скелетон показывает «призрак» будущего интерфейса, снижает «прыжок» контента (layout shift) и выглядит современнее.

**Примеры из проекта:**

- **Карточки каталога** — `CardSkeleton count={4}`. Пользователь видит сетку заглушек с картинками и текстом, понимает, что грузится каталог курсов.
- **Страница курса** — `TextSkeleton lines={5}`. Пользователь видит «призрак» текста описания курса, а не пустой экран.

### 🔄 Спиннер (`Spinner`)

Используем, когда действие **быстрое** или **локальное** (кнопка, строка, небольшой блок). Спиннер не пытается имитировать контент — он просто говорит «подожди».

**Примеры из проекта:**

- **Кнопка «Записаться»** — `Spinner variant="inline" size={20}`. Пока запрос отправляется, внутри кнопки крутится маленький спиннер, а текст меняется на «Отправка...». Скелетон здесь не нужен — кнопка и так маленькая.
- **Быстрая подгрузка** — если данные приходят из кэша или запрос занимает < 300 мс, спиннер не нужен вообще (показываем сразу данные).

### 💡 Краткое правило

| Ситуация                                              | Что использовать                              | Почему                                     |
| :---------------------------------------------------- | :-------------------------------------------- | :----------------------------------------- |
| Загружается список карточек / таблица / большой текст | **Скелетон** (`CardSkeleton`, `TextSkeleton`) | Показывает структуру, снижает layout shift |
| Загружается кнопка / строка / небольшой блок          | **Спиннер** (`Spinner variant="inline"`)      | Компактно, не отвлекает                    |
| Загружается целая страница (нет контента вообще)      | **Спиннер** (`Spinner variant="block"`)       | Простой индикатор «подожди»                |

## Индикаторы при переходах (навигация)

Текущее состояние: переходы между страницами происходят мгновенно, так как все компоненты загружены в основном бандле. **Индикатор перехода сейчас не нужен** — он будет только создавать визуальный шум.

**План на будущее (эпик 12 — ленивая загрузка):**

- **Переход между страницами (`useNavigation`)**:
  - Когда страницы начнут загружаться лениво (`lazy`), при переходе будет возникать задержка.
  - В этот момент нужно показывать **скелетон страницы** (например, `CardSkeleton` или `TextSkeleton` в зависимости от типа страницы). Это даёт пользователю понять, что переход начался, и показывает структуру будущего контента.
  - Реализация: в корневом layout-компоненте (рядом с `<Outlet />`) использовать `useNavigation()`. Если `navigation.state === 'loading'`, рендерить скелетон вместо `<Outlet />` (или поверх него).

- **Первичная загрузка приложения**:
  - Когда пользователь впервые открывает сайт, браузер скачивает основной JS-бандл. В это время показывать **спиннер** (`Spinner variant="block"`), так как структура страницы ещё неизвестна.
  - Реализация: в `index.html` или в корневом компоненте до монтирования роутера.
